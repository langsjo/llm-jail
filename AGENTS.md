# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test

```bash
nix build .#claude              # Build the runner script
nix run .#claude -- --help      # Show CLI usage
nix flake check                 # Validate flake structure and run all tests
```

The runner tests that boot a jail (`runner-boot`, `runner-rc`, `runner-protect`, `runner-network`, `runner-lifecycle` in `tests/runner.nix`) run inside NixOS test VMs, where a `host` VM runs the runner as an unprivileged user, the way a real host does: the runner needs `/dev/net/tun`, which the Nix build sandbox lacks. `runner-network` adds an `internet` VM. The jail is then a nested VM, so they need nested KVM to be fast. Build one with e.g. `nix build -L .#checks.x86_64-linux.runner-boot`.

End-to-end test (needs a terminal and a prior in-jail login - run `nix run .#claude` once and complete the login flow, which persists credentials in `~/.config/llm-jail/claude/default`):
```bash
nix run .#claude -- --dangerous -- -p "Write hello to /workspace/hello.txt" --max-turns 3
```

After changes to guest NixOS config, rebuilds are fast (only systemd units regenerate). Changes to `flake.nix` inputs or `writeShellApplication` trigger full rebuilds.

## Architecture

This is a Nix flake that runs coding agents inside QEMU microVMs with hardware-level isolation. No persistent disk images - the guest boots on a tmpfs root (or a throwaway ext4 image with `--disk`) with the host's `/nix/store` shared read-only via virtiofs (see Key Constraints). An overlayfs covers `/nix/store` with its upper layer on the root filesystem, so under `--disk` everything the guest writes outside the host mounts lands on disk rather than in RAM.

**Data flow:** `flake.nix` iterates `tools.nix`, builds a NixOS guest system per tool, wraps each with `lib/mkRunner.nix` into a QEMU launcher script.

**Host side (`lib/mkRunner.nix`):** A `writeShellApplication` that parses CLI args at runtime, creates a private `$RUNDIR` (mode 700), starts one `virtiofsd` per share, optionally creates a root disk image, and starts QEMU in the background with direct kernel boot, inside a per-run network namespace (see Key Constraints). Only `$RUNDIR/share` (env file, tool args, allowlist, the per-run public key, ...) is shared with the guest, as the envfs at `/llmjail-env`; the per-run ed25519 private key, `ssh_config`, the QEMU socket `ssh.sock` and the ssh control socket stay host-only in `$RUNDIR`. The runner then starts an ssh master (`ssh -f -M -N`) whose ProxyCommand is `socat` on `ssh.sock`, the host end of the `llmjail.ssh` virtserialport; the master's login completing is the boot wait. The tool runs as a multiplexed session on that master (`-t` when stdin and stdout are terminals, else `-T`), and the runner prints an `ssh -F $RUNDIR/ssh_config jail` command for inspection shells. When the session ends, the runner closes the master (`-O exit`), which makes the guest power off, and kills QEMU only if it is still running after 15 s. If the VM fails to boot or the connection is lost, `print_guest_logs` prints `qemu.log`, the virtiofsd logs and the tails of `dnsmasq.log` and `guest.log` (kernel console plus forwarded journal), all through `cat -v` because the guest controls their text. On NixOS hosts, `/run/current-system/sw` and `/etc/profiles/per-user/$USER` are auto-mounted so host packages are available in the guest.

**Guest side (`guests/common.nix` + `guests/claude.nix`):** Minimal NixOS. `llmjail-mounts` parses kernel cmdline (`llmjail.mounts=tag:path:mode,...`) to mount user directories via virtiofs and installs the per-run public key as `/etc/ssh/authorized_keys.d/user`, or `.../root` with `llmjail.root=1` (`--root`) (root-owned, 0444). It must succeed before `llmjail-ready.target` (`Requires=`) and carries `FailureAction=poweroff-force`, so a failed setup powers the VM off instead of opening a session. The guest enforces no boundary itself: its network is a static address behind the host's filter. `llmjail-sshd` runs `sshd -i` with stdin/stdout on `/dev/virtio-ports/llmjail.ssh` (only key login, as `user` or with `--root` as root, no listener anywhere in the guest; the stock `sshd.service` is not started and `systemd.ssh_auto=no` disables systemd's ssh generator). Its `ExecStopPost` powers the VM off when the connection closes. The session command is the `llmjail.launcher` option: it sources `/etc/set-environment` and `/llmjail-env/env`, then execs `llmjail.toolBinary` with the tool args. The journal is forwarded at `info` to the second serial port, which QEMU writes to `$RUNDIR/guest.log` together with the kernel console.

**Adding a new tool:** Add an entry to `tools.nix` pointing to a new guest module under `guests/`. The guest module imports `common.nix` and sets `llmjail.toolBinary`.

## Key Constraints

- **The tool's terminal is an ssh session over a virtserialport, not a console.** QEMU's `virtconsole` silently drops guest output when the host fd can't absorb a burst (`hw/char/virtio-console.c`, unfixed as of QEMU 11.0.1), which corrupted TUI frames; a `virtserialport` throttles instead. ssh over that port gives the session a real pty, window-size forwarding, and a second (inspection) session through multiplexing. One multiplexed stream was chosen over vsock: no host daemon, no shared guest memory, and no listener inside the guest the agent could reach. The QEMU socket chardev serves one client, so everything goes through the master. Only `$RUNDIR/share` is shared with the guest, so the private key and `ssh_config` never reach it. ssh runs ProxyCommand through `$SHELL`, which in tests (and for some users) is not a POSIX shell, so `jail_ssh` sets `SHELL` to the runtime shell. The poweroff lives in `llmjail-sshd`'s `ExecStopPost` rather than a command sent over ssh, because the agent controls the user's shell. Targets cannot fail, so `FailureAction=` sits on the setup services, not on `llmjail-ready.target`. QEMU, virtiofsd and the master's proxy run under `setsid` (with `setpriv --pdeathsig KILL`): QEMU installs its own SIGINT handler over the ignore bash gives background jobs, and ssh forks its proxy before daemonizing, so either would otherwise get the terminal's Ctrl-C and drop the connection.

- **Every boundary is enforced on the host, never in the guest.** `--root` runs the session as root in the guest, so anything the guest kernel enforces (nftables, bind mounts, file modes) would be decoration. The runner refuses to start without unprivileged user namespaces (it test-mounts in one, which also catches Ubuntu 23.10+'s AppArmor stripping their capabilities) or `/dev/net/tun`.
- **The network filter lives on the host, in a per-run namespace** (`lib/net.nix`, addresses in `lib/addresses.nix`). `llmjail-net` re-executes itself under pasta, which creates a user+network namespace and carries its traffic to host sockets; inside, it creates the tap `jail0` for the guest, loads the `inet llmjail` nft table (forward chain = the policy; input chain admits only DNS to the gateway; the `blocked` set always refuses loopback, link-local, `0.0.0.0/8`, multicast; refused traffic gets a TCP reset or ICMP admin-prohibited, so clients fail at once), starts dnsmasq (allowlist + `nftset`, settings on its command line; empty `--user=`/`--group=` because setgroups is denied there), then execs QEMU with no capabilities. pasta's defaults would reach host loopback through the gateway address and through `-T auto` port forwarding, hence `--no-map-gw -t none -u none -T none -U none`. The NIC uses `vhost=off`, so guest packets are not parsed by host kernel vhost code. `$!` is pasta, which exits with QEMU; QEMU and dnsmasq carry `--pdeathsig KILL`. The nft set has no timeout on purpose: re-adding an element does not renew it, so entries would expire under clients holding cached answers.
- **Masks and protected git files are applied on the host, in front of each virtiofsd** (`lib/share.nix`, tested without a VM by `tests/share.nix`). `llmjail-share` re-executes itself in a user+mount namespace owned by the invoking user, bind-mounts read-only copies over the files host git executes code from (config, config.worktree, hooks, submodule gitdirs, worktree configs; created read-only if missing) and empty read-only files/dirs from a namespace-private tmpfs over `--mask` matches, then drops every capability and execs virtiofsd, whose nested sandbox locks those mounts. Read-only binds come first so masks inside them land on top. Paths are resolved once at startup; anything created later is not covered.
- **virtiofs is the only file sharing** (9p was removed). The runner starts one unprivileged `virtiofsd --sandbox=namespace` per share, so the host must allow unprivileged user namespaces (Ubuntu 23.10+ blocks them via AppArmor by default). That namespace maps only the invoking user, so guest uids/gids are squashed to the host user and unowned host files appear as root. Caching is chosen host-side per share mode (`--cache`), not by guest mount options. The store share runs with `--no-announce-submounts`: announced submounts become automount points in the guest, which overlayfs rejects in its lower layer (`EREMOTE`), so a host `/nix/store` containing mounts (e.g. inside a Nix build sandbox) would hide every store path. Guest RAM must be a shared memfd (`memory-backend-memfd,share=on`) for vhost-user. virtiofsd stderr goes to `$RUNDIR/virtiofsd-<tag>.log` and is printed with the other logs only when the VM fails to boot or the connection is lost.
- **virtiofs can't mount single files.** `.gitconfig` is copied into the envfs temp dir on the host and copied out to `$HOME` by the guest mounts service.
- **Tool args use null-separated files** (`tool-args`) to preserve argument boundaries through the host→guest boundary. Don't use env vars for args with spaces.
- **`/run` is remounted by systemd in stage 2**, so guest share mounts must not go under `/run`. The envfs mount is at `/llmjail-env`.
- **`writeShellApplication` runs shellcheck.** Avoid `compgen` and other builtins that shellcheck flags. Use `env | grep` patterns instead.
- **The root filesystem is chosen at runtime, not in the guest config.** The guest has no `fileSystems."/"` and sets `boot.initrd.systemd.root = null`; the runner appends `root=tmpfs rootflags=mode=0755` (unsized, so up to half the guest RAM) or, with `--disk SIZE`, `root=/dev/vda rootfstype=ext4 rw` for systemd's initrd fstab-generator (`rw` because it mounts block-device roots read-only otherwise). `--store-disk` is a deprecated alias for `--disk`. The disk gives space for large builds (`/nix/var/nix/builds/`), `$HOME` caches and Docker images.
- **Dev shell environments can be captured on the host and sourced in the guest:** `nix print-dev-env` (opt-in with `--nix-env`) for plain nix flakes/shells, or `devenv direnv-export` (opt-in with `--devenv`, requires `--same-path`) for devenv.sh projects — both write to the same `dev-env` file the guest sources. `devenv direnv-export` (undocumented but stable - it's what devenv's own maintained direnvrc uses internally to import a devenv shell into direnv's already-running shell) was chosen over `devenv shell` specifically because its output has no trailing `exec` to worry about, unlike `devenv shell`'s generated rcfile which always ends by replacing the sourcing shell. devenv still bakes the workspace's absolute host path into `DEVENV_ROOT`/`DEVENV_DOTFILE`/`DEVENV_STATE`, which `--same-path` keeps valid in the guest.
- **The host store mount and overlay upper live outside `/nix/store`.** The host store is mounted read-only at `/.nix-lower/store` (used as the overlay lower layer directly - overlayfs does not reliably cross submount boundaries, so the lower must be the mounted filesystem itself). The overlay upper and work dirs are `/.nix-upper/store` and `/.nix-upper/work` on the root filesystem. Keep this in mind when debugging mount issues inside the guest.
- **Tool state is jail-private.** Each tool's state lives in a host dir `~/.config/llm-jail/<tool>/<profile>` (never the host tool's own config), mounted read-write at `/home/user/<configDirName>`. The tool is relocated into it via its native env var (`configEnvVar` in `tools.nix`, e.g. `CLAUDE_CONFIG_DIR` or `AUTOLITH_HOME`), which `mkRunner.nix` writes into the env file that the launcher sources. A tool whose state spans several dirs (opencode's XDG layout, or Autolith's XDG-derived state/data/cache dirs) points the remaining dirs into the same mount via exports in its launcher wrapper (see `guests/opencode.nix`). A tool that keeps no state (the debug shell) simply omits `configDirName`/`configEnvVar` and gets no config mount or `--config-dir`/`--profile` flags. Never mount a directory the host tool also uses read-write - a jailed agent could plant hooks/settings the host tool would execute.
- **`.llmjailrc` needs approval because the agent can write it.** The workspace is read-write, so without a check a jailed agent or a cloned repo could widen the next run's jail (`--no-net-filter`, `--mount`, or host code through `--devenv`). Masking the file was rejected: it dirties `git status`, breaks checkouts, and misses a rc arriving through a commit or in a subdirectory. `~/.config/llm-jail/approved-rc` holds `<sha256>  <cwd>` lines, and approving replaces the cwd's previous line so an agent can't silently restore an older approved rc (e.g. through git); it sits outside every `<tool>/<profile>` state mount, so the guest can't reach it. Declining aborts instead of continuing without the file, which may contain restrictions like `--mask`. Argument order comes from calling `parse_args` once per source (rc, then CLI), not from concatenating them, so each `--` only ends its own source.
- **Docker (`.docker` build arg) is rootless.** `guests/docker.nix` enables NixOS's `virtualisation.docker.rootless` user unit, started at boot by lingering `user`. A rootful daemon would no longer weaken the jail (the boundaries are on the host), but rootless keeps default runs free of root. Container egress leaves through slirp4netns and the guest's NIC, so the host's filter applies unchanged. `DOCKER_HOST` points at `/run/llmjail-docker.sock`, a symlink `llmjail-docker-ready` creates, so it also works in `--root` sessions. `linger-users` must run after `llmjail-set-user-uid` (`loginctl enable-linger` resolves the uid that user@ starts under). user@ reports ready at basic.target, before the daemon is up, so `llmjail-docker-ready` waits for the socket before the session starts. Guest modules can add whitelisted domains through `llmjail.extraAllowedDomains`, which mkRunner reads from the guest config.
